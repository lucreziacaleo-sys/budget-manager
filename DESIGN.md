# Design Rationale

The key architectural decision is a layered design where validation happens only at the boundaries. Every transaction, whether typed into the CLI or read from the CSV file, goes through the same `validate_create_transaction` function before it becomes a `Transaction` object. This means the service layer can trust that everything it holds is already valid, and the rules live in one place instead of being scattered across modules. Each layer has one job: the CLI only handles prompts and printing, the service only handles business rules (no duplicate IDs, totals per currency), and storage only reads and writes files. This is why each part can be tested on its own, without typing anything into the menu. Following the principle of never silently correcting data, the sample file is treated as read-only and the user's data is saved to a separate `transactions.csv`, so invalid sample rows are never erased without a warning. For the same reason, the summary shows totals per currency instead of adding EUR and USD together into a number that means nothing.
